# Taste
- Uses Brave as their primary browser (Chromium-based); targets Chromium for web tooling rather than Firefox/Safari. Confidence: 0.6
- For automating web workflows, prefers a browser extension over a server-side/CLI/backend approach. Confidence: 0.5
- Favors lean, framework-free toolchains — approved a plain TypeScript + esbuild + Vitest setup over WXT/React-style frameworks for a browser extension. Confidence: 0.4
- Prefers distributing tools as a GitHub release zip loaded unpacked via `chrome://extensions`, not via app-store submission — explicitly to avoid vendor review and platform-rule exposure for a legally/policy-sensitive (e.g. torrent-related) tool; the release asset is the entire distribution channel. Confidence: 0.75
- Dislikes redundant intermediate steps in a workflow: wants the action (e.g. a download) surfaced inline at the point of decision instead of forcing navigation through extra pages. Confidence: 0.5
- When handing over large throwaway reference artifacts (e.g. a pasted page DOM dropped into the repo), expects the agent to extract what is needed and then delete the file — no scratch dumps left behind or committed. Confidence: 0.5
- Wants injected UI (e.g. browser-extension controls) to blend with the host page: inherit the page's font/size and look native rather than appear as browser-default buttons, and to sit inline immediately after the item they act on (e.g. right after a title) instead of at the end of the row. Confidence: 0.55
- Expects injected controls to behave like the host site's own native elements so the browser's built-in affordances work on them — e.g. a resolved magnet rendered as a real `magnet:` link so the native right-click "Copy link address" and drag work exactly as they do on a torrent site — rather than a bespoke control that only mimics the appearance. Confidence: 0.45
- Evidence before implementation: when offered "build it now against generic/assumed selectors and verify later" versus "paste the real markup first", chose to wait for the real captured artifact. Prefers code written against observed input over speculative assumptions, even at the cost of a pause. Confidence: 0.6
- Personally exercises the built artifact in the browser (reloading the extension, refreshing the host page) and reports back concrete symptoms observed there — expects those reports to be treated as real evidence, not just as questions. Confidence: 0.6
- Prefers batched delivery over incremental check-ins: wants all remaining work items completed in one pass and verified together at the end, rather than pausing for per-item confirmation or step-by-step verification rounds ("complete all items we verify all at once"). Confidence: 0.7
- Wants debug logging built into the tool (a namespaced logger with a single on/off switch, logging ids/URLs/statuses only) so failures can be diagnosed from the console without a live browser session. Confidence: 0.5
- Docs before code: expects a written spec change (a numbered decision entry in the decision log with context, decision, explicitly rejected alternatives, and consequences, plus updated architecture invariants) to land before any implementation starts. Confidence: 0.5
- Holds changes to mutant-proof evidence: every new test is expected to be shown failing when the behaviour it covers is reverted, and a claim with no test able to catch its regression is treated as unfinished work. Confidence: 0.55
- Wants verification by a separate, read-only agent that does not fix what it finds, reports pass/fail per acceptance criterion with real command output, and cannot be satisfied by the implementer's own summary. Confidence: 0.5
- Prefers low-risk, incremental changes that leave existing contracts (message/API shapes, request types) untouched and add no new dependencies, over new surface area that buys only a marginal win. Confidence: 0.45
- Communication preference: wants unsoftened findings and explicit disclosure of what is still unverified/untested, rather than tidy summaries that hide gaps. Confidence: 0.5
- Leaves finished work uncommitted in the working tree and reports it as such (what changed, check exit code, test count) instead of committing or pushing unprompted; the commit/push happens only after an explicit go-ahead ("its fine push the change"). Confidence: 0.5
- Comfortable with direct commits pushed straight to `main` — no branch/PR review ceremony — once they've approved, and expects post-push state (CI run result) to be confirmed rather than assumed. Confidence: 0.4
- Treats runtime performance as a first-class design concern: asks explicitly how a change behaves on low-spec/low-end machines and whether it is "too costly", and expects real measured numbers (benchmarks on the actual modules) rather than reassurance. Confidence: 0.5
- Wants a downloadable release to be self-explanatory: the zip should carry a step-by-step install README (and the license) so an unzipping user is met with instructions rather than a folder of code, and the artifact should be the ready-to-load build — not a source tree that makes users install a toolchain and build it themselves. Confidence: 0.6
- Prefers to ship and tag a release rather than gate it on a pending manual acceptance test, testing the exact published artifact (a failure becoming the next patch release) instead of holding the tag until every browser-only check has passed. Confidence: 0.45
